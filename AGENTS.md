# potli

potli is an npm-compatible registry for scoped packages (`@scope/name`), on one Cloudflare Worker.
npm, pnpm, bun and yarn install from it and `npm publish` to it with no plugin. A website shows
each package's README and versions, and lets people sign in with GitHub to manage scopes and
publish tokens. What users care about most: installs never break, and published versions never
change. Stack: TanStack Start (React) for the site, Hono for the npm API, D1 + Drizzle, R2, Better
Auth (GitHub), PostHog, Vitest in workerd, bun.

## Words we use

- **you**: the agent reading this file.
- **me**: the developer you are working for.
- **user**: the person who installs or publishes packages. Not me.
- **scope**: the `@name` part of a package name. Every package is in one. A user owns the scope
  matching their GitHub login and can claim free org scopes.
- **packument**: the JSON document `GET /@scope%2fname` returns: every version's manifest plus
  dist-tags.
- **manifest**: one version's package.json as published, plus `dist`.
- **tarball**: the `.tgz` that `npm pack` makes. Lives in R2, keyed by package and version.
- **token**: a publish token for npm clients. Only its SHA-256 is stored.

## Map

| Where | What lives there |
|---|---|
| `src/server.ts` | Worker entry: `/@...` and `/-/...` go to the registry, everything else to the site |
| `src/features/registry/` | npm API (Hono): packuments, tarballs, publish, whoami, search |
| `src/features/auth/` | Better Auth config and client |
| `src/features/<name>/` | one folder per feature: UI, logic, data access, tests |
| `src/routes/` | TanStack Start file routes. Thin: render a feature, nothing else |
| `src/db/schema.ts` | Drizzle schema, the one source of data types. Auth tables are generated |
| `drizzle/` | SQL migrations, generated by `bun run db:generate`. Never hand-edit |
| `test/` | Vitest setup: test Worker entry, migrations for each test file |
| `scripts/` | `setup.mjs`, `doctor.mjs`, `remove-worktree.mjs`; `local-d1.mjs` reads local migrations |
| `docs/` | `registry-protocol.md` (read before touching the registry), `decisions.md`, `ops.md` |

Each feature lives in one folder with its UI, logic, data access and tests. Shared code goes in
`src/lib/` only when two features really use it.

## Commands

- Install: `bun install`
- Setup a fresh worktree: `bun run setup` (installs deps, copies `.dev.vars` and `.env.local` from
  the main checkout, picks a free port, migrates this checkout's local D1)
- Doctor: `bun run doctor` (run it first when anything looks off)
- Remove a worktree, from another checkout: `bun run remove-worktree <path>` (stops its dev
  processes, removes the `.claude/skills` link alone, then the worktree; `--force` drops
  uncommitted changes)
- Dev: `bun run dev` (port from `PORT` in `.env.local`; ready when Vite prints `Local:`)
- Seed local data for the website: `bun run seed` (@kausthubh and @kriyan packages from real READMEs, local D1 only)
- Test one file: `bunx vitest run src/features/registry/registry.test.ts`
- Typecheck and lint: `bun run typecheck`, `bunx biome check <files>`
- New migration after a schema change: `bun run db:generate`, then `bun run db:migrate`
- After changing `wrangler.jsonc` or the names in `.dev.vars`: `bun run cf-typegen`
- Full check (CI runs this after `bun run build`; run it only when asked): `bun run check`

## Proving a change works

- Done means you saw it work, not that it compiles. For the registry that means a real client:
  `npm publish` and `bun add` against your dev server. For the site, open the page.
- Use the `verify-potli` skill to launch, drive and capture evidence. If it does not exist yet,
  run `/create-verification-skill`.
- Test with real-shaped data: publish real tarballs (`npm pack` on a real package) into your local
  registry. An empty database is a bad test.
- Registry tests run inside workerd with real local D1 and R2 (`@cloudflare/vitest-plugin`). Call
  the Hono app the way npm does (`registry.request(...)`) and assert the exact JSON.
- A test calls the code the way its users do and asserts the exact result. Delete tests that
  would pass if every function returned undefined.
- Never edit or delete a test to make it pass. If the test is wrong, say so and explain why.
- A skipped check is not a pass. Report what you ran, what you saw, and what you did not check.

## How we write code

- Boring and explicit over clever. If it is not written where it happens, you cannot see it.
- One way to do each thing. Finish migrations and delete the old way in the same change.
- A wrapper with one caller is just another file to open. Inline it.
- Names you can grep. No barrel `index.ts` files except `src/db/index.ts`.
- Comments say why, never what.
- Smallest change that solves the real problem. No scope creep.
- Workers: stream tarballs, never buffer them. Background work goes in `ctx.waitUntil`. Secrets
  come from `.dev.vars` and `wrangler secret`. `Env` comes from `wrangler types`, never
  hand-written. Random tokens come from `crypto.getRandomValues`.

## Rules and what enforces them

| Rule | Enforced by |
|---|---|
| Published versions never change | publish returns 409 for an existing version; registry test |
| Only scoped package names | registry routing; registry test |
| Tarball URLs use the request origin, never a fixed domain | registry test |
| Website paths never start with `/@` or `/-/` | `isRegistryPath` routing in `src/server.ts` |
| No `any`, no non-null assertions | Biome |
| Types come from the schema and `wrangler types` | TypeScript strict |

When I correct you for the same thing twice, add the rule here and make something enforce it
(`/correct`).

## Cloud sessions

potli runs on Linux as well as on my Windows laptop: setup, the doctor, `remove-worktree`, dev,
build and the full check all work there. A cloud VM (Claude Code on the web, Codex Cloud) starts
from a bare clone. The SessionStart hook in `.claude/settings.json` runs `node scripts/cloud.mjs`
(Codex: set the environment's setup script to `CLOUD=1 node scripts/cloud.mjs`). It loads my global
skills and rules, then runs setup. It does nothing outside the cloud. Its last line says ready or
what failed; rerun it if you're unsure.

- A bare clone is its own main checkout, so setup makes `.dev.vars` from `.dev.vars.example` with a
  fresh `BETTER_AUTH_SECRET`, and gives it port 3000.
- Works there: setup and the doctor, `bun run dev`, `bun run build`, `bun run check`, the registry
  with real `npm`/`bun` clients against the dev server, and the site through dev sign-in
  (`DEV_LOGIN=1` is in the example; add your test login to `SIGNUP_ALLOWLIST` in `.dev.vars`).
- Start dev in its own process group so stopping it stops vite and workerd too:
  `setsid --fork sh -c 'echo $$ > .wrangler/dev.pid; exec bun run dev' > .wrangler/dev.log 2>&1 < /dev/null`,
  then `kill -TERM -- -$(cat .wrangler/dev.pid)`. One dev server takes about 1.3 GB; on a shared
  machine run one at a time.
- `bun run seed` reads the real READMEs from the repos next to the main checkout (`critly`,
  `megha`, `kriyan`). A bare clone has none; point `POTLI_SEED_SOURCES` at a folder that does.
- Env vars: none needed. GitHub sign-in needs `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET` in
  `.dev.vars`, which a cloud VM doesn't have; use dev sign-in.
- Only on my machine: production (`ship-potli`'s deploy and `--remote` commands need my wrangler
  login) and the main checkout. List those steps in your report.

## Safety

- Never touch production data: the remote D1 `potli` and the R2 bucket `potli-tarballs`. Local dev
  uses `.wrangler/state` in your checkout. Never pass `--remote` to wrangler.
- Production needs my explicit go: deploys, `--remote` commands, secrets, releases. Prod commands
  live in `docs/ops.md`.
- Stop only processes you started, by the PID you captured. Never kill by name or by port.
- No secrets in code, logs, screenshots or commits. `.dev.vars` and `.env.local` stay untracked.
- Git: public repo. Open a PR and wait for CI and my review.
